# Profile command verification

Each entry records that a variant's declared commands were run against a real
installation of that framework version and behaved as the profile assumes.
An unverified variant still works - it is just not yet known to be correct.

| wordpress | | | | not yet verified; requires per-project `sanitize.rules` override for the production URL. **Optional tables:** none - the users table always exists unconditionally, but it is not necessarily *named* `wp_users`: WordPress's table prefix is configurable (`$table_prefix` in wp-config.php, default `wp_`). `anonymize-users` and `reset-user-passwords` no longer hardcode `wp_users` - both now use the `${WP_TABLE_PREFIX}` placeholder (operations/placeholders.py), which resolves `database.wp_table_prefix` if a project sets it, otherwise reads *production's* `table_prefix` over the same ssh round trip `database.remote_credentials: wp_cli` already uses for credentials (operations/database.py's `_from_wp_cli`), memoised so it costs nothing extra beyond what db.dump and the preflight probe already pay for. **Not** read from the local checkout: a WordPress repo conventionally gitignores wp-config.php and DDEV regenerates one with the default `wp_` prefix, so a local read would silently report the wrong value on exactly the hardened installs this exists for. **Not** `wp db prefix` either: that returns the current *site's* prefix, which differs from `base_prefix` on a multisite install, and the users table is named from `base_prefix` specifically (it lives in `wpdb::$global_tables`, not the per-site `$tables` - confirmed against wp-cli/config-command's `Config_Command.php`, which also confirmed `--type=variable` is required to disambiguate `table_prefix` from a same-named constant, since `--type` defaults to `all` and errors on the ambiguity). `anonymize-users` declares `requires_table: "${WP_TABLE_PREFIX}users"`, so a wrong prefix now fails at the preflight probe (operations/preflight.py) before the dump starts, naming the missing table and the rule that needs it, rather than silently leaving every real email and password hash untouched with the database already imported. ## Known limitations

- `mysqldump --password=` is visible in the remote host's process list for the
  duration of the dump. Fixing it properly means writing a temporary
  `--defaults-extra-file` on the remote, which reintroduces the remote temporary
  file that streaming removed. Accepted for now; revisit if a target environment
  makes process-list exposure unacceptable.
