# Profile command verification

Each entry records that a variant's declared commands were run against a real
installation of that framework version and behaved as the profile assumes.
An unverified variant still works - it is just not yet known to be correct.

A verified row claims only what its run showed. *Notes* separates what has
run-time evidence (and of which kind: an exit status, or an effect observed in
the database or on disk) from what was only exercised through a tolerance such
as `tolerate_missing_table`, and from what no run touched. Where a command is
`allow_failure`, or its exit status is discarded (`flush_cache`), the engine
reports it as fine whether or not it worked, so only an observed effect counts
as evidence for it. The evidence columns are filled by `python -m
tools.apply_verified_rows` from a green matrix cell (`tests/matrix/`); the
framework versions are whatever Composer resolved on the day, so a row says
when it was true. The six filled rows' *Verified against* and *By* cells were
written by hand with the installed versions and the run's timestamp, because
`--emit` yields only `<image> on <php image>`; a row emitted by CI will say
less than they do.

## Feature command verification

Features are not profile variants, so they get their own table rather than
rows mixed into the one above: a feature's granularity is "this package is
present", not "this framework major version", and forcing one into the
other's columns would blur what was actually checked.

## Known limitations

- `mysqldump --password=` is visible in the remote host's process list for the
  duration of the dump. Fixing it properly means writing a temporary
  `--defaults-extra-file` on the remote, which reintroduces the remote temporary
  file that streaming removed. Accepted for now; revisit if a target environment
  makes process-list exposure unacceptable.
